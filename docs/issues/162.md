# Issue 162: Multi-Provider LLM Routing Ignores Active Provider

**Status:** Resolved
**Date:** January 23, 2026
**Epic:** 11 - Multi-Provider LLM Support
**Discovered:** Manual testing in staging

---

## Problem Statement

When using the multi-provider LLM feature with a non-OpenRouter provider (e.g., Anthropic), the app would:
1. Allow navigating to the home page
2. But clicking "Start New Quiz" would fail with "Not connected to OpenRouter"
3. Quiz generation was blocked even though Anthropic was properly configured with a valid key

---

## Root Cause Analysis

### Bug 1: `isConnected()` Only Checked OpenRouter

**File:** `src/services/auth-service.js:13-15`

The function only checked if OpenRouter was connected:
```javascript
export async function isConnected() {
  return isOpenRouterConnected();
}
```

This caused `HomeView.js` to redirect users to OpenRouter setup even when another provider was configured.

### Bug 2: `getApiKey()` Only Returned OpenRouter Key

**File:** `src/services/auth-service.js:21-23`

The function only returned the OpenRouter API key:
```javascript
export async function getApiKey() {
  return getOpenRouterKey();
}
```

This caused `LoadingView.js` to fail the API key check before quiz generation, even though the active provider (Anthropic) had a valid key configured.

---

## Solution Design

### Fix 1: Update `isConnected()` to Check Active Provider

```javascript
export async function isConnected() {
  // Check if the active provider has a key configured
  const activeProvider = await getActiveProvider();
  if (await hasProviderKey(activeProvider)) {
    return true;
  }

  // Fallback: check OpenRouter for backward compatibility
  return isOpenRouterConnected();
}
```

### Fix 2: Update `getApiKey()` to Return Active Provider Key

```javascript
export async function getApiKey() {
  // Get the key for the active provider
  const activeProvider = await getActiveProvider();
  const key = await getProviderKey(activeProvider);
  if (key) {
    return key;
  }

  // Fallback: OpenRouter key for backward compatibility
  return getOpenRouterKey();
}
```

## Lessons Learned

1. **Backward compatibility layers can create blind spots** - The auth-service was designed for OpenRouter-only operation. When adding multi-provider support, each function that checks connection/key status needs to be reviewed.

2. **Feature flag testing is essential** - This bug only appeared when the `MULTI_PROVIDER_LLM` feature flag was enabled. Testing with feature flags on and off is important.

3. **Service layer abstraction matters** - The auth-service provides a clean interface (`isConnected`, `getApiKey`) that views depend on. Updating these central functions fixed the issue across multiple views.
