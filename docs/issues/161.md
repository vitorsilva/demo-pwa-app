# Issue 161: Anthropic API Key Validation Fails for Valid Keys

**Status:** Resolved
**Date:** January 23, 2026
**Epic:** 11 - Multi-Provider LLM Support
**Discovered:** Manual testing in staging

---

## Problem Statement

When attempting to configure an Anthropic API key in the LLM Providers settings, valid API keys were incorrectly rejected with the error "Invalid API key format. Keys should start with 'sk-ant-'."

Additionally, when keys did pass client-side validation, the backend proxy returned generic 500 errors instead of meaningful HTTP status codes, making debugging difficult.

---

## Root Cause Analysis

### Bug 1: Client-Side Regex Too Restrictive

**File:** `src/api/providers-config.js:63`

The regex pattern for validating Anthropic API keys was:
```javascript
keyPattern: /^sk-ant-[a-zA-Z0-9-]+$/
```

This pattern did **not** include underscores (`_`), which are valid characters in real Anthropic API keys. For example:
```
sk-ant-api03-meDm-eUBehBLfyR54fY2zcDMeS-a5iAEsz6SHap2JJDl3wK7fa_Mo0Ui9xv7...
                                                              ^
                                                          underscore here
```

### Bug 2: Backend Returns Generic 500 Errors

**File:** `php-api/llm/completion.php`

The error handling caught all exceptions and returned a generic response:
```php
http_response_code(500);
echo json_encode(['error' => 'Internal server error']);
```

This hid useful information like:
- 401 for invalid API keys
- 429 for rate limiting
- 400 for malformed requests

---

## Solution Design

### Fix 1: Update Regex Pattern

Add underscore to the character class:
```javascript
// Before
keyPattern: /^sk-ant-[a-zA-Z0-9-]+$/

// After
keyPattern: /^sk-ant-[a-zA-Z0-9_-]+$/
```

### Fix 2: Improve Backend Error Responses

Parse exception messages and return appropriate HTTP status codes:
- **401** - Invalid API key
- **429** - Rate limit exceeded
- **400** - Invalid request / missing fields
- **502** - Network error connecting to provider
- **500** - Other server errors (fallback)

## Lessons Learned

1. **Real-world API key formats vary** - Always test with actual production keys, not just examples from documentation. The underscore character is common in API keys but was missed.

2. **Generic error responses hide problems** - Backend should return specific HTTP status codes to help with debugging and provide better user feedback.

3. **Browser DevTools MCP is invaluable** - Using Chrome DevTools MCP to inspect network requests and console errors quickly identified both the client-side regex failure and the backend 500 error.
