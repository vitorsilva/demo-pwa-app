## Problem

The Party Mode backend (PHP + MySQL) stores session data for room management and WebRTC signaling. A cleanup script already exists (`php-api/party/cleanup.php`) but **no cron job is configured on the VPS** to run it automatically, which means stale/abandoned party sessions accumulate in the database over time.

## Proposed Solution

Configure a cron job on the VPS to periodically clean up old party session data.

### Data to Clean
- Expired/abandoned rooms
- Old signaling messages
- Disconnected peer records
- Any other temporary party session data

### Considerations
- Retention periods already configured in `php-api/party/config.php`:
  - Rooms: 2 hours (`room.expiry_hours`)
  - Signaling messages: 60 seconds (`signaling.message_expiry_seconds`)
- Script suggests running every 15 minutes (see comment in `cleanup.php`)
- Cleanup script already exists and logs operations to stdout

## Solution Design

### Existing Cleanup Script

The cleanup script already exists at `php-api/party/cleanup.php` and:
1. Ends rooms older than `expiry_hours` (default 2 hours)
2. Deletes signaling messages older than `message_expiry_seconds` (default 60 seconds)
3. Deletes old rate limit records
4. Logs cleanup operations to stdout

### Current Retention Policy (in `config.php`)

| Data Type | Retention | Config Key |
|-----------|-----------|------------|
| Rooms | 2 hours | `room.expiry_hours` |
| Signaling messages | 60 seconds | `signaling.message_expiry_seconds` |

### Cron Schedule (recommended)

Run every 15 minutes:

**Via cPanel (Cron Jobs):**
1. Log in to cPanel
2. Navigate to **Cron Jobs** (under "Advanced" section)
3. Set schedule: `*/15 * * * *` (every 15 minutes)
   - Or use the dropdowns: "Every 15 minutes", "Every hour", "Every day", "Every month", "Every weekday"
4. Set command:
   ```
   /usr/bin/php /home/USERNAME/public_html/app/php-api/party/cleanup.php >> /home/USERNAME/public_html/app/php-api/party/logs/cleanup.log 2>&1
   ```
   - Replace `USERNAME` with your cPanel username
   - Adjust path if your app is in a different location
5. Click **Add New Cron Job**

**Notes:**
- Create the `logs` directory first if it doesn't exist
- Use full paths (cPanel cron doesn't have the same PATH as interactive shell)
- Find PHP path with cPanel's "Terminal" or ask hosting support (usually `/usr/bin/php` or `/usr/local/bin/php`)

## Testing Plan

### Manual Testing (Required)

**Justification:** This is a backend operational task that requires VPS access. Automated testing is impractical due to:
- Requires MySQL database with test data
- Requires cron execution environment
- Involves time-based operations

### Manual Testing Checklist

- [ ] Cleanup script runs without errors
- [ ] Old rooms are deleted (create test room, wait, verify deletion)
- [ ] Active rooms are NOT deleted
- [ ] Old signaling messages are deleted
- [ ] Cleanup is logged to file/stdout
- [ ] Cron job executes on schedule
- [ ] No impact on active party sessions

### Verification Steps

**Via cPanel:**
1. **Check cron is configured:**
   - Go to cPanel → Cron Jobs
   - Verify the cleanup job appears in "Current Cron Jobs" list

2. **Run manually to verify (via cPanel Terminal or File Manager):**
   - Option A: Use cPanel Terminal (if available):
     ```bash
     php ~/public_html/app/php-api/party/cleanup.php
     ```
   - Option B: Access via browser with token:
     ```
     https://saberloop.com/app/php-api/party/cleanup.php?token=YOUR_CLEANUP_TOKEN
     ```
     (Set `CLEANUP_TOKEN` env var on server first)

3. **Check logs:**
   - Go to cPanel → File Manager
   - Navigate to `public_html/app/php-api/party/logs/`
   - View `cleanup.log` file
